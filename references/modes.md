# 六大模式的算法与口径

本文件是 `lib/modes.js` 的说明文档，按需查阅。每个模式都对应一条**真实**的麦当劳 MCP 调用链，所有计算都在 `lib/modes.js` 内完成，前端只负责渲染。

统一返回结构：

```js
{
  id, title, subtitle,
  chain: [{ tool, ok, ms, error }],   // 真实调用记录
  costMs,                              // 端到端总耗时
  blocks: [...],                       // 渲染规格
  raw: {...}                           // 关键数值（便于调试）
}
```

`blocks` 支持 6 种类型：`hero` / `kpi` / `table` / `bars` / `list` / `note`。

## 1. `mci-index` · 中国麦价指数 McIndex

**调用链**：`now-time-info` → `query-nearby-stores` → `query-meals`

### 门店解析

1. `query-nearby-stores { beType:1, searchType:1 }` — 收藏门店
2. 若返回空（错误码 `600050`），回退 `searchType:2` + `city` + `keyword`

### 篮子构成

指数口径 = **主食 + 小食 + 饮品**三件套的现价合计。

每个品类有优先级关键词列表和**排除正则**，避免类目串台：

| 品类 | 关键词（按优先级） | 排除 |
|---|---|---|
| 主食 · 汉堡 | 巨无霸 → 安格斯 → 麦辣鸡腿 → 板烧鸡腿 → 双层吉士 → 麦香鸡 → 猪柳蛋 → 炒双蛋 → 麦满分 → 汉堡 | 薯条/可乐/雪碧/豆浆/牛奶/咖啡/橙汁/圆筒/新地/麦旋风/派/鸡块/鸡翅 |
| 小食 · 薯条/鸡块 | 中薯条 → 大薯条 → 小薯条 → 薯条 → 麦乐鸡 → 鸡块 → 鸡翅 | 堡/麦满分/汉堡/卷/套餐/可乐/雪碧/豆浆/牛奶/咖啡/橙汁/麦旋风/新地 |
| 饮品 · 汽水/果汁 | 中可乐 → 中雪碧 → 可乐 → 雪碧 → 橙汁 → 柠檬茶 → 豆浆 → 牛奶 | 堡/麦满分/汉堡/薯条/麦乐鸡/鸡块/鸡翅/套餐 |

**命中规则**：在每个关键词下，先滤掉套餐类（`套餐|组合|三件套|两件套|四件套|派对|礼盒`），再取**名字最短、价格最低**的那个 —— 这样"巨无霸"不会选成"巨无霸可乐套餐"。命中首个关键词记为标准基准，否则标为「替代（命中「X」）」。

> 为什么小食要排除「堡」和「麦满分」？因为实测"原味板烧鸡腿麦满分"包含"鸡腿"二字，会被误判成小食，导致篮子里出现两个汉堡。

**缺品类处理**：某品类在本时段无在售单品时，**从篮子中剔除并在结论里点名**，不拿其他商品硬凑。

### 其他输出

- **折扣商品占比** = 原价 > 现价的商品数 ÷ 在售商品数
- **单品价格 TOP 10**、**折扣力度 TOP 8**（按 `原价 − 现价` 排序）
- 时段判断 `guessDaypart()`：<10 点早餐 / <14 点午餐 / <17 点下午茶 / 其余晚餐夜市

### 已知局限

菜单随供餐时段变化（早餐/正餐/夜宵菜单不同），因此同一门店不同时段的读数不严格可比。跨期对比建议固定在同一时段取数。

## 2. `annual-report` · 麦当劳年度账单

**调用链**：`order-list` → `list-nutrition-foods`

### 订单归集

遍历 `order-list` 返回的 `list[]`：

- 主商品：`orderProductList[].{productName, quantity}`
- 套餐子项：`comboItemList[].{name|productName, quantity}`（也会计入单品频次）

### 统计口径

| 指标 | 口径 |
|---|---|
| 订单数 | `list.length` |
| 总消费 | `Σ realTotalAmount`（不含麦麦商城订单） |
| 客单价 | 总消费 ÷ 订单数 |
| 涉及门店 | `storeName` 去重计数 |
| 时间跨度 | 最早与最晚 `createTime` 相差天数 |
| 月度分布 | 按 `createTime.slice(0,7)` 分组求和 |

### 热量估算

营养表返回的是伪表格文本，`parseNutrition()` 按表头解析：

```
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
```

匹配方式：`fuzzyFind()` 做**名称归一化后的双向包含匹配** —— 归一化会去掉 `【】（）""·、,，。-_/` 及"汉堡/套餐/组合/小杯/中杯/大杯"等噪声词，然后在候选里选**长度差最小**的一个。

| 折算 | 系数 | 说明 |
|---|---|---|
| 跑步公里 | 60 kcal / km | 约 60kg 体重慢跑 |
| 米饭碗数 | 230 kcal / 碗 | — |

### 已知局限

热量为**估算值**：匹配是模糊的，套餐子项可能匹配不到，区域限定品不在营养表内。匹配件数会一并展示，便于判断可信度。

## 3. `points-advisor` · 积分理财师

**调用链**：`query-my-account` → `mall-points-products{catRuleIds:"1>4"}` → `query-lottery-info`

### 关键参数

`catRuleIds` 必须传 `"1>4"`（商品券），否则默认返回的是**现金商品**（`point=0`），拿不到积分兑换券。可选值：

| 值 | 含义 |
|---|---|
| `1>4` | 商品券（非预付优惠券） |
| `2` | 实物商品 |
| `2>8` | 周边产品 |
| `2>9` | 实物礼品卡 |
| `1>6>20` | 生日类派对 |

### 性价比计算

券名里带着面值，用正则抠出来：

```
"18.8元麦辣鸡腿汉堡两件套"  →  面值 18.8 元，所需积分 50  →  0.3760 元/分
"10.9元指定小食任选"       →  面值 10.9 元，所需积分 100 →  0.1090 元/分
```

`每积分价值 = 面值 ÷ 所需积分`。无面值的商品（如"为随心配五大巨星应援 1 积分兑换活动"）不参与排行。

### 过期止损折算

```
机会成本 = 已过期积分 × 当前最优兑换率
```

实测：1360.7 分 × 0.3760 元/分 ≈ **¥511.62**。

### 抽奖与不做的计算

`drawPoint`（单次消耗）实测 24 分，可抽次数 = `floor(可用积分 ÷ drawPoint)`。

**抽奖期望值不给数字** —— 奖品概率不公开，静态算不出可信期望值，所以只给"能抽几次"和奖品池。

## 4. `fulfillment-compare` · 三路比价器

**调用链**：`query-nearby-stores`×2 → `delivery-query-addresses` → `delivery-query-stores` → `query-meals`×N → `calculate-price`×N

### 三条路径的参数差异（最容易踩的坑）

| 路径 | `beType` | `orderType` | `beCode` | 门店来源 |
|---|:--:|:--:|---|---|
| 到店自取 | 1 | 1 | **不传**（传了报错） | `query-nearby-stores{beType:1}` |
| 得来速 | 5 | 1 | **必传** | `query-nearby-stores{beType:5, searchType:2}` |
| 麦乐送 | 2 | 2 | **必传** | `delivery-query-stores{addressId, beType:2}` |

得来速的收藏门店常为空，需回退到城市+关键词搜索。

### 篮子选取（关键）

三条路的菜单**商品集合不同**，所以先求**商品 code 交集**，再按品类各取一件：

| 品类 | 匹配正则 | 优先关键词 |
|---|---|---|
| 主食 | `堡|卷|麦满分|汉堡` | 巨无霸 / 板烧鸡腿 / 麦辣鸡腿 / 猪柳蛋 / 麦香鸡 / 双层吉士 |
| 小食 | `薯条|麦乐鸡|鸡块|鸡翅|派` | 中薯条 / 薯条 / 麦乐鸡 |
| 饮品 | `可乐|雪碧|橙汁|豆浆|牛奶|柠檬茶` | 中可乐 / 可乐 / 橙汁 / 豆浆 |
| 咖啡 | `咖啡|拿铁|美式|卡布|摩卡` | 美式 / 拿铁 |

最后用高价商品补足到 4 件。

> 为什么不能按"匹配分数"排序？第一版就是这么做的，结果同款交集里全是麦咖啡，篮子严重失真。

### 差价来源（本模式最有价值的发现）

到店菜单与外送菜单**同款商品标价本身不同**。实测同一门店同款商品：

```
到店菜单 currentPrice = 21.50 元
外送菜单 currentPrice = 23.50 元
```

所以差价不只来自"配送费 + 打包费"，还来自**标价差**。这是用户几乎无从知晓的一层。

### 金额单位

`calculate-price` 返回**分**（`productPrice` / `deliveryPrice` / `packingPrice` / `discount` / `price`），`query-meals` 的 `currentPrice` 是**元字符串**。分别用 `cents2yuan()` 与 `menuYuan()` 转换。

### 失败降级

三条路各自 `try/catch`。某条路不可用（无门店、无配送范围）时，在结果表里标「不可用：原因」，其余路径照常对比，并在末尾追加一条说明。

## 5. `coupon-lifecycle` · 券生命周期管家

**调用链**：`available-coupons` → `query-my-coupons` → `(query-nearby-stores → query-meals)`

### 券值计算（核心）

`query-my-coupons` 返回的券带 `discountInfo`：

```json
{ "discountValue": "9.9", "discountDesc": "用券价格", "discountTypeText": "¥" }
```

注意 `discountDesc` 是 **"用券价格"** 而不是"立减金额"——它表示**券后要付多少钱**。所以：

```
立省 = 门店菜单价 − 用券价
```

实现上：

1. `coreName` = 券名去掉 `套餐|两件套|三件套|四件套|组合|早餐|超值|单人|双人|指定`
2. 先用完整券名匹配菜单，失败再用 `coreName`
3. `saving > 0` → 展示「省 ¥X」
4. `saving ≤ 0`（券后价 ≥ 菜单价）→ 标「券后价 ≥ 菜单价（品类可能不同）」，提示匹配存疑
5. 完全匹配不到 → 标「未匹配到同款」，**不编造差价**

若 `discountDesc` 含"减/省/折"则为立减金额，直接取作 `saving`。

**归并展示**：同一张券名可能是多个独立券实例（不同到期日），表格按 `券名 + 对应餐品 + 菜单价 + 用券价 + 立省` 归并成一行，列出「张数」与「最近到期」，避免同名行刷屏。

### 临期计算

```
临期天数 = ceil((tradeEndDateTime − now) / 86400000)
```

档位：`< 0` 已过期 / `≤ 1` 今明到期 🔴 / `≤ 7` 临期 🟠 / 其余充裕 🟢

### 未领清点

`available-coupons` 里 `couponStatus !== 'HAVING_RECEIVE'` 的即为可领未领。仅**提示**用户去领，不调用 `auto-bind-coupons`。

## 6. `calorie-coach` · 热量预算教练

**调用链**：`list-nutrition-foods` → `query-nearby-stores` → `query-meals`

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `options.budget` | 600 | 热量预算（kcal） |
| `options.priceCap` | 45 | 价格上限（元） |

### 商品池

菜单 94 款 × 营养表 160 条做 `fuzzyFind` 匹配，命中且有热量的进入池子（实测 57 款）。

### 组合穷举

枚举**1~3 件**的全部组合（含重复计数），约束：

```
热量 ≤ budget  且  价格 ≤ priceCap  且  热量 ≥ 50 kcal
且 组合内至少含一件主食（正则：堡|卷|麦满分|汉堡|鸡块|薯条|饭|鸡翅|鸡腿|派|豆浆|粥）
```

最后一条是**为了避免"最轻负担"给出一杯黑咖啡（13 kcal）这种凑数解**。

实测 57 款商品 → **4858 种**可行组合。

### 三套方案

| 方案 | 排序依据 |
|---|---|
| 🏆 用满预算 | 热量最大 |
| 🪶 最轻负担 | 热量最小 |
| 💰 每卡最省 | `价格 ÷ 热量` 最小 |

同一热量+价格只保留一套。

### 折算

跑步公里 = 热量 ÷ 60（约 60kg 体重慢跑）。**这是粗估**，个体差异大，结论里已注明。

## 附：通用工具函数

| 函数 | 作用 |
|---|---|
| `cents2yuan(c)` | 分 → 元 |

## 附：MCP 返回体解析

MCP 的 `tools/call` 返回可能有两种形态：

- `result.structuredContent` —— 干净的业务 JSON（**优先使用**）
- `result.content[0].text` —— 文本，含 `## Original Response` 段包裹的 JSON（回退解析）

失败判定：`structuredContent.success === false` 时视为失败，错误信息取自 `message` + `code`。

统一封装在 `lib/mcp.js` 的 `callTool()` 里，**永不抛异常**，一律返回 `{ ok, ms, tool, args, data, error }`。
